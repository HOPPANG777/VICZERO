## 오늘 한 일

Project-ZFC의 맵을 만들기 전에 어떤 데이터가 어디에 있어야 하는지부터 정리했다. `Map`이 모든 것을 들고 있게 만들면 처음에는 편해 보여도 플레이어, 적, 공격 예고, 렌더링까지 서로 얽히게 된다. 그래서 지형은 `Map`, 유닛 상태는 각 유닛, 여러 상태를 조합한 행동 판정은 `CombatSystem`, 화면 출력은 `ConsoleRenderer`가 맡도록 책임을 나눴다.

## 빠른 요약

```text
Map은 지형을 소유하고 질문에 답한다.
Unit은 자신의 상태를 소유한다.
CombatSystem은 여러 상태를 조합해 행동을 검증한다.
Renderer는 상태를 변경하지 않고 화면에서만 합성한다.
```

한 좌표에 지형, 점유, 효과가 동시에 존재할 수 있으므로 이들을 하나의 `TileType`에 몰아넣지 않는다. 현재 `TileType`은 `NONE`, `WALL`, `FLOOR`처럼 지형만 표현한다.

## 핵심 개념

### 1. 데이터의 소유자는 하나로 정한다

맵 크기를 `size`와 `tiles`에 동시에 저장하면 둘이 달라질 수 있다. 따라서 `tiles`를 단일 진실 공급원으로 두고 높이는 `tiles.size()`, 너비는 비어 있지 않을 때 `tiles.front().size()`에서 구한다.

### 2. 좌표와 컨테이너 크기는 역할이 다르다

좌표는 `(0, 0)`에서 왼쪽으로 갔을 때 `(-1, 0)`을 표현해야 하므로 signed 타입인 `int`가 필요하다. `size_t`는 원소 개수와 안전한 인덱스에 사용한다. 음수와 범위를 먼저 검사한 뒤에만 컨테이너에 접근한다.

### 3. 2차원 vector는 `tiles[y][x]`로 읽는다

바깥 vector는 행의 목록이고 안쪽 vector는 한 행의 열 목록이다. `(x, y)` 좌표를 vector에 적용할 때는 행인 `y`를 먼저 선택한다.

### 4. Map은 유효한 상태를 보장해야 한다

모든 행의 길이가 같고, 외부에서 행의 길이를 임의로 바꿀 수 없으며, `TILE_NONE`이 실제 지형으로 사용되지 않는 것이 기본 불변 조건이다. 이 조건을 생성 시점에 한 번 보장하면 조회 함수가 단순해진다.

### 5. 함수 계약은 실패 입력까지 포함한다

- `GetSize`: 너비와 높이를 반환한다.
- `Contains`: 음수와 행·열 범위를 순서대로 검사한다.
- `TileAt`: 유효 좌표의 지형을 반환하고, 현재 정책에서는 범위 밖이면 `TILE_NONE`을 반환한다.
- `IsWalkable`: 허용할 지형인 `TILE_FLOOR`만 명시적으로 `true`로 판단한다.

## 오늘 발견한 실수

- 비 `void` 함수의 모든 실행 경로에 반환값을 작성하지 않았다.
- `size()`를 마지막 인덱스로 착각할 수 있었다.
- `(x, y)`와 `tiles[y][x]`의 순서를 혼동했다.
- `IsWalkable()` 마지막 반환값을 잘못 두면 모든 타일이 통행 가능해질 수 있었다.
- C++의 `0 <= x < width`는 수학식처럼 동작하지 않으므로 조건을 `&&`로 나눠야 한다.
