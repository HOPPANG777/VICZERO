## 오늘 한 일

7월 13일에는 `Map`이 지형을 소유하고 질의 기능을 제공한다는 기본 책임을 정했다. 오늘은 그보다 앞 단계인 “어떤 데이터가 Map이 될 자격을 가지는가”를 결정했다. 빈 Map, 서로 다른 행 너비, 내부 `TILE_NONE`을 허용하지 않고 검증된 `TileLayout`을 통해서만 `Map`을 생성하도록 경로를 설계했다.

## 빠른 요약

```text
TileGrid는 만들어 가는 데이터다.
TileLayout은 구조 검증이 끝난 불변 타일 배치다.
Map은 TileLayout을 소유하고 지형 질문에 답한다.
MapFactory는 검증되지 않은 데이터가 Map이 되는 것을 막는다.
MapGenerator는 절차적 후보의 품질을 책임진다.
CombatState는 unique_ptr로 Map을 단독 소유한다.
Renderer는 Map을 소유하지 않고 읽기만 한다.
```

## 핵심 개념

### 1. 안전한 상태와 유효한 상태는 다르다

빈 `Map`이 범위 밖 접근 없이 `(0, 0)`과 `false`를 반환한다고 해서 게임에서 의미 있는 상태인 것은 아니다. 아직 생성되지 않음, 생성 실패, 로딩 중 같은 상태는 상위 시스템이 별도로 표현하고, `Map`이 존재하면 유효한 지형이 완성된 것으로 취급한다.

### 2. Map의 불변 조건

- 행이 하나 이상 존재한다.
- 열이 하나 이상 존재한다.
- 모든 행의 너비가 같다.
- 내부에 `TILE_NONE`이 없다.
- 크기를 프로젝트 좌표 타입으로 표현할 수 있다.
- 외부에서 행과 타일을 임의로 변경할 수 없다.

FLOOR 존재 여부, 연결성, 스폰 가능성은 구조 조건이 아니라 생성 품질이나 전투 준비 조건이다.

### 3. 검증을 세 단계로 나눈다

- `MapFactory`: 데이터가 올바른 직사각형 지형인지 구조를 검증한다.
- `MapGenerator`: 방, 통로, 연결성 등 절차적 후보의 품질을 검증한다.
- `CombatSetup`: 특정 전투의 유닛과 보스를 실제로 배치할 수 있는지 검증한다.

이 경계를 지키면 Map 생성기가 적 정의나 특정 전투 규칙까지 알 필요가 없다.

### 4. 후보 탈락과 구조 오류는 다르다

방 연결 실패나 공간 부족은 무작위 생성에서 예상 가능한 후보 탈락이므로 다른 시드로 제한 횟수만 재시도할 수 있다. 빈 행, 비정형 행, 남아 있는 `TILE_NONE`은 구현 버그나 설정 오류에 가까우므로 무한 재시도로 숨기지 않는다.

### 5. 검증 전후 데이터를 타입으로 구분한다

`TileGrid`는 아직 잘못된 상태일 수 있는 가변 데이터다. `TileLayout`은 검증을 통과해야만 만들어지는 불변 배치다. `MapFactory`가 이 경계를 통제하면 호출자가 검증을 우회해 `Map`을 만드는 경로를 줄일 수 있다.

### 6. 결과 타입의 계약

`MapGenerationResult`는 절차 생성 후보의 성공과 탈락을 표현한다. `MapCreationResult`는 구조 검증 성공 여부와 완성된 `unique_ptr<Map>`을 전달한다.

허용되는 상태:

```text
성공 -> Map 존재
실패 -> Map 없음
```

성공인데 Map이 없거나 실패인데 Map이 있는 상태는 허용하지 않는다.

### 7. 접근과 소유는 다르다

여러 시스템이 같은 Map을 읽어도 공동 소유가 필요한 것은 아니다. `CombatState`가 `unique_ptr<Map>`으로 수명을 책임지고, `CombatSystem`, `Renderer`, `CombatSetup`은 필요한 동안 읽기 전용 참조만 사용한다.

### 8. C++ 도구의 정확한 의미

- `explicit`: 암시적 형 변환을 제한하지만 데이터를 검증하지는 않는다.
- `stdexcept`: 표준 예외 타입을 제공하며 `throw` 자체를 제공하는 것은 아니다.
- `std::move`: 데이터를 직접 옮기지 않고 자원 이전이 가능하다는 의도를 표현한다.
- 참조 전달: 객체를 빌리는 것이며 소유권 이전을 뜻하지 않는다.

## 내가 잘한 점

- 이전 학습에서 보류한 질문을 잊지 않고 다음 설계 작업으로 연결했다.
- 불규칙한 맵 모양과 비정형 저장 구조를 구분해 그리드는 직사각형으로 유지했다.
- 검증 실패 데이터를 자동으로 수정하지 않는 원칙을 정했다.
- 재시도 횟수, 대체 맵, 실패 시드 로그까지 상위 로딩 흐름을 고려했다.
- 그래픽 자원 실패를 Map 구조 실패와 섞지 않아 API 이식성을 유지했다.

## 보완할 점

- 문서의 클래스와 결과 계약을 실제 C++ 타입으로 구현해야 한다.
- `MapCreationStatus`의 구체적인 상태 목록과 진단 정보 형태를 결정해야 한다.
- `TileLayout`의 읽기 인터페이스와 Map 사이에 불필요한 래핑이 생기지 않는지 코드로 확인해야 한다.
- 설계 문서가 계속 커지지 않도록 다음 단계에서는 최소 구현과 테스트를 우선해야 한다.
