## 빠른 요약

```text
퀘스트·보스·이벤트
-> TryAcquireSkill
-> 획득 Flag 저장
-> 제단에서 반납 가능 기술 조회
-> TryReturnSkill
-> 반납 Flag 저장
-> 재건도와 복원 단계 계산
-> ES3 Save
```

기획과 Unity 콘텐츠가 아직 없어도 검증 가능한 도메인, 저장, 최소 UI 기반을 먼저 만들었다. 실제 유적 외형과 연출은 추측해서 구현하지 않았다.

## 핵심 학습

### 계산 가능한 값은 중복 저장하지 않는다

재건도는 반납된 기술의 `RestoreValue` 합계로 다시 계산할 수 있다. 재건도 숫자와 반납 상태를 함께 저장하면 둘이 어긋날 수 있으므로 반납 Flag만 영속화한다.

### 상태 변경 진입점을 하나로 모은다

퀘스트가 Progress Flag를 직접 설정하지 않고 재건 서비스의 `TryAcquireSkill`을 호출한다. 보스와 이벤트도 같은 진입점을 사용하면 중복 획득과 잘못된 ID 처리가 한곳에서 유지된다.

### 고정 데이터와 진행 상태를 분리한다

기술 ID, 챕터, 재건도 증가량, 복원 임계값은 Catalog와 SO의 고정 데이터다. 획득·반납 여부는 플레이 진행 상태다. 서로 다른 수명과 변경 주기를 가진 데이터를 한 객체에 넣지 않았다.

### 저장은 시점과 경쟁 상태까지 설계해야 한다

실제 값이 바뀔 때만 Dirty가 되고 퀘스트 보상, 기술 반납, 씬 전환 전에 저장한다. 저장 도중 새로운 변경이 발생해도 이전 저장 완료가 새 Dirty를 지우지 않도록 버전을 비교한다.

### 최소 UI도 실패 경로를 포함해야 한다

제단 UI는 고정 버튼을 재사용하고, 확인 연속 입력과 저장 중 닫기를 차단하며, 실패나 예외가 발생해도 `finally`에서 플레이어 조작을 복구한다.

### 기획 공백을 코드로 덮지 않는다

유적의 정체, 제단 명칭, 복원 외형, Timeline, 엔딩과 텔레포트 규칙이 정해지지 않았다. 이 상태에서 콘텐츠 구조를 만들면 재작업 가능성이 높으므로 기반 코드에서 멈췄다.

## 잘한 점

- 새로운 Manager나 싱글턴을 늘리지 않고 기존 `GameRoot`와 서비스 구조를 사용했다.
- UI를 열 때마다 생성·삭제하지 않고 고정 풀과 버퍼를 재사용했다.
- 실제 파일 I/O에만 UniTask를 사용하고 조회 API에서 저장을 발생시키지 않았다.
- 테스트와 줄 수 검사를 기존 단일 테스트 파일에 통합해 계획 제한을 지켰다.
- 기획이 필요한 부분과 프로그래머가 먼저 확정할 수 있는 부분을 구분했다.
