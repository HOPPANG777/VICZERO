## 오늘 한 일

Project Ruin 저장소의 Branch, Commit, Issue, PR, Git LFS와 Unity 파일 관리 상태를 확인했다. 기존에도 Commit을 작업 단위로 나누고 본문을 꼼꼼하게 작성하고 있었지만, 그것은 다른 팀원이 반복해서 사용할 수 있는 규칙이라기보다 좋은 개인 습관에 가까웠다. 이를 기획자와 개발자가 함께 사용할 수 있도록 Issue와 PR 중심의 흐름으로 문서화했다.

## 빠른 요약

```text
Issue에서 목적과 완료 조건을 정한다.
작업 목적이 드러나는 Branch에서 수정한다.
Commit과 Push로 작업을 공유한다.
PR에서 결과와 검증 방법을 설명한다.
Review 후 Squash merge로 release에 반영한다.
```

핵심은 Git 기능을 많이 쓰는 것이 아니라, 역할별로 필요한 기능만 사용하고 모든 변경이 검토 단계를 지나도록 만드는 것이다.

## 핵심 개념

### 1. 개인 습관과 팀 규약은 다르다

개인이 Commit을 잘 작성해도 다른 사람이 같은 방식으로 반복할 Template과 절차가 없다면 팀 규약이라고 보기 어렵다. 팀 규약에는 문서, 역할과 책임, 적용 조건, 예외 처리, Review 절차, 실수를 막는 저장소 설정이 필요하다.

### 2. Issue의 완료 조건은 기획과 개발 사이의 계약이다

`기능 구현 완료`처럼 추상적인 문장은 검토하기 어렵다. 어떤 선택지가 표시되어야 하는지, 저장 후에도 결과가 유지되는지처럼 실제로 확인 가능한 조건을 적으면 개발자는 범위를 이해하고 기획자는 코드를 읽지 않아도 결과를 검토할 수 있다.

### 3. 상태와 분류를 분리한다

- Project 상태는 작업이 현재 어디까지 진행됐는지를 나타낸다.
- Label은 작업 종류, 담당 분야, 우선순위를 나타낸다.

같은 정보를 Project와 Label 양쪽에서 관리하면 갱신할 곳만 늘어난다.

### 4. Branch 이름에는 작업 목적이 들어가야 한다

작업자와 버전만 들어간 `0.0.1-VicZero`보다 `feature/12-dialogue-choice`처럼 Issue 번호와 목적이 들어간 이름이 업무와 변경 기록을 연결하기 쉽다.

### 5. PR 품질과 Squash merge로 최종 기록을 관리한다

Git 초보자에게 모든 중간 Commit을 완벽하게 요구하면 작업 부담이 커진다. 대신 PR 제목, 본문, 확인 결과를 정확히 작성하고 Squash merge를 사용하면 안정 Branch에는 작업 목적이 분명한 하나의 Commit을 남길 수 있다.

### 6. Unity의 `.meta`는 핵심 데이터다

Unity는 `.meta`의 GUID로 Scene, Prefab, Sprite, Script 참조를 연결한다. Git LFS가 설정되어 있어도 `.meta`가 무시되면 참조 문제는 해결되지 않는다. 에셋과 폴더의 `.meta`를 함께 추적해야 하며, 기존 `.meta`를 임의로 재생성해서도 안 된다.

### 7. Scene과 Prefab 충돌은 사전에 줄인다

Unity YAML 충돌은 해결하기 어렵다. 같은 Scene이나 Prefab을 여러 사람이 동시에 수정하지 않도록 Issue에 영향 범위를 적고 작업을 분담하는 것이 우선이다.

## 오늘 확인한 실제 문제

- Issue와 PR 사용 이력 및 Template이 없었다.
- `release`에 직접 Push하지 못하게 하는 보호 설정이 없었다.
- 병합 방식이 세 종류 모두 허용되어 팀 기준이 없었다.
- `.gitignore`의 `*.meta` 때문에 약 15,871개의 `.meta`가 무시되고 있었다.
- 결과 Commit의 제목과 본문은 GitHub 문서만 설명했지만 코딩 컨벤션과 Unity 설정 변경도 함께 포함됐다.

## 내가 잘한 점

- 일반론이 아니라 실제 저장소 상태와 기존 작업 기록을 먼저 확인했다.
- 기존의 좋은 Commit 습관은 유지하면서 부족한 Review 단계를 추가했다.
- 기획자의 역할을 업무 관리와 파일 수정으로 나눠 학습 부담을 줄였다.
- `.meta` 문제를 발견하고 곧바로 대량 추가하지 않고 별도 안전 작업으로 분리했다.
- 결과 Commit을 다시 열어 규약을 어긴 부분까지 스스로 찾아냈다.

## 보완할 점

- 규약 문서만으로는 직접 Push나 잘못된 Merge를 막을 수 없으므로 저장소 설정을 적용해야 한다.
- `.meta` 규칙을 수정한 뒤 새 Clone에서 참조가 유지되는지 검증해야 한다.
- Commit 직전에 포함 파일 전체가 하나의 목적에 속하는지 확인해야 한다.
- 실제 기획자와 개발자가 테스트 Issue를 수행해 문서가 정말 이해하기 쉬운지 확인해야 한다.
